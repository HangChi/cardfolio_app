# Feature 010 账号与本地优先同步设计

## 目标与边界

卡迹在未登录、断网、同步暂停和远端故障时仍以 Drift 本地数据库作为唯一读取源。
登录只解锁可选同步，不改变现有保存路径。同步覆盖业务数据和受管图片；令牌、诊断
内容和本地文件路径不进入同步载荷。

本仓库交付客户端、可替换 REST 协议、Supabase 服务端权限/表结构基线和契约测试。
生产环境通过 `CARD_FOLIO_API_BASE_URL` 注入 HTTPS 服务地址，不把服务密钥编译进 App。

## 方案比较与决策

比较了两种托管方案：

- Supabase：Postgres、Auth、Storage 与 RLS 在同一项目内，私有对象可用签名 URL，
  数据模型与现有关系型 Drift 更接近；客户端离线队列需由卡迹实现。
- Firebase：Firestore 客户端自带离线持久化，但多设备同文档冲突是 last-write-wins，
  与“同字段冲突保留双方”的规则不一致；关系模型、计费读取和供应商 SDK 绑定更强。

选择 Supabase 作为首个服务端实现，同时冻结 Cardfolio REST 协议作为客户端边界。
客户端不直接依赖 Supabase SDK，后续可替换自建服务。正式部署前必须重新核对地区、
费用和 DPA。证据来源记录在 ADR-009。

## 组件

- `AccountSyncRemote`：注册、登录、刷新、退出、账号删除、push、pull 和附件接口。
- `SecureSessionStore`：只保存访问/刷新令牌，生产实现使用平台安全存储。
- `SyncLocalStore`：从完整逻辑快照发现本地变化，维护 outbox、服务端基线、游标和冲突。
- `AccountSyncRepository`：编排认证、附件、push/pull、指数退避和冲突解决。
- `ProfileScreen`：展示本地模式、账号、同步开关、积压、失败、冲突和危险操作。

## 数据流

本地写入仍先提交原有业务事务。一次同步开始时，`SyncLocalStore` 对 16 类用户数据与
最近确认的服务端基线做差异，首次发现变更时生成持久化 UUID 操作 ID；重试复用该 ID。
push 成功后才更新基线并删除 outbox。随后按游标 pull，逐项在本地事务中应用。

若本地和远端相对共同基线修改不同字段，自动合并并把合并结果重新入队；同字段取值
不同、删除/修改碰撞则写入冲突副本，原本地数据不被覆盖。用户可保留本地、采用远端
或提交显式合并载荷。退出账号默认只清令牌、停同步并保留本地数据。

## 安全与失败

仅接受 HTTPS 生产地址；认证令牌不写 Drift、普通偏好、URL 或日志。服务端每张表按
`user_id = auth.uid()` 执行 RLS，附件位于用户私有前缀。401 触发一次刷新；网络、5xx
和 429 保留 outbox 并指数退避；协议错误和权限错误显示脱敏错误码，不丢弃变更。
删除账号必须二次确认，服务端先停止新写入并清云端数据，之后再按用户选择清理本地。

## 测试

纯 Dart/SQLite 测试覆盖 20 条离线创建、重复重放、断点游标、时钟偏差、同字段与
删除冲突、退出保留本地、账号删除选择、附件校验和与退避。REST 使用受控 HTTP
客户端做请求/响应契约测试；Widget 测试覆盖账号、开关、状态、冲突和二次确认。
模拟器/真机只保留为手动网络切换、安全存储和进程重启步骤。
