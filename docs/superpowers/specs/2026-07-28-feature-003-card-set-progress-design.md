# Feature 003 套卡与完成度设计

日期：2026-07-28

## 目标与边界

在既有 `CardDefinition → CardItem → CardImage` 模型上增加套卡聚合，不复制卡片资料，也不持久化完成度缓存。Feature 003 交付套卡资料、成员关系、实时完成度和管理界面；系列、购买、统计与回收站 UI 留给后续 Feature。

## 方案选择

采用“成员关系引用款式定义”。已有成员直接引用现有 `CardDefinition`；尚未拥有的成员创建只有定义、没有 `CardItem` 的款式。这比仅用预计总数推算缺失更能表达成员名称、编号和必需性，也避免以数量为 0 的伪藏品污染收藏统计。

采用“查询时聚合完成度”。`CardSetMember` 保留必需性与顺序，查询聚合未删除 `CardItem.quantity`。重复数量不会扩大已拥有款式数，软删除和恢复会自然触发 Drift 数据流重算，不需要维护易失效的百分比列。

## 组件边界

- 领域层：套卡请求、成员请求、摘要、详情、候选款式和纯完成度值对象。
- 数据层：`card_sets`、`card_set_members`、schema v3 迁移、事务和响应式聚合查询。
- 仓储层：输入规范化、数据库错误映射和 UTC/版本协调。
- 展示层：收藏页“卡片/套卡”切换、套卡表单、详情进度和成员管理。

## 数据流

创建套卡时预生成 UUID 并单事务写入。关联已有款式只写成员；定义缺失成员时在同一事务写款式定义和成员。详情查询把成员、活跃藏品和封面图片组合为快照，再由纯领域函数计算已拥有、缺失、重复和完成状态。

## 不变量

- 活跃套卡名称非空。
- 未知总数不保存预计数量，不产生百分比或完成状态。
- 已知预计数量不小于活跃成员数量。
- 同一套卡与款式只有一个活跃成员关系。
- 成员顺序连续且排序请求包含完整、唯一的活跃成员 ID 集合。
- 套卡封面属于当前活跃成员的活跃图片。

## UI 方向

沿用现有米色背景、深绿主色、橙色次要强调和 Material 3 字体层级。详情以纵向“成员清单轨道”作为识别点：状态节点配合文字区分已拥有、缺失与重复；进度区用明确分数而不是只用颜色。布局不固定画板高度，支持窄屏和 200% 字体。

## 错误与测试

可预期输入与关系冲突使用 `CardSetValidationFailure`，数据库事务使用 `PersistenceFailure`，读取失败使用 `DatabaseUnavailableFailure`。自动化覆盖领域规则、真实 SQLite、v2→v3 迁移、仓储、Riverpod/Widget 和 AC-P0-005；模拟器、真实重启和读屏留作用户手动验收。
