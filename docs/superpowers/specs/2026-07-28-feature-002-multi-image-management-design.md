# Feature 002 多图与封面设计

日期：2026-07-28

## 目标与边界

在 Feature 001 的本地三实体闭环上增加多图管理，不引入相机或图片处理。系统相册负责多选，App 私有目录继续保存不可变原图，SQLite 保存用途、顺序、封面和删除状态。

## 方案选择

采用“独立封面标记 + 独立连续排序”。把封面等同顺序第一项虽然实现简单，但用户设封面会意外改变图集顺序；把封面 ID 放在 `CardItem` 会引入循环外键和更复杂迁移。`CardImage.isCover` 配合事务及活跃封面部分唯一索引，能直接表达业务规则。

采用“保留原图即软删除图片行”。单独建立保留文件注册表会增加一套生命周期；完全不保留又违背原图默认保留策略。软删除行既能让图集隐藏图片，又能让启动孤儿清理继续保护文件。

## 组件

- 领域层：六种 `CardImageKind`、多图写入请求、删除影响和图片查询模型。
- 平台层：`GalleryPicker.pickMany(limit)` 隔离 `image_picker`。
- 数据层：schema v2、迁移、活跃图片查询以及追加/用途/排序/封面/删除事务。
- 仓储层：协调批量文件导入、数据库提交和补偿删除。
- 展示层：创建页多图草稿；详情页图集与管理操作。前移/后移作为拖拽的键盘和读屏等价操作。

## 数据流

创建或追加时预先生成图片 ID，按 ID 把源文件导入 `originals/<cardItemId>/`，全部成功后在一个事务写入元数据。数据库失败会删除本批次文件。设置封面和排序仅操作数据库。删除原图时先提交数据库变化，再删除文件；删除失败的无引用文件由启动清理再次处理。

## 不变量

- 活跃图片数为 1..20。
- 活跃图片顺序为 `0..n-1` 且 ID 不重复。
- 每个藏品恰有一个活跃封面。
- 封面变化不改变顺序。
- 原图路径唯一、相对且不可被派生处理覆盖。

## 错误与验证

可预期输入问题使用 `ValidationFailure`，文件问题使用 `ImageImportFailure`，事务问题使用 `PersistenceFailure`。自动化覆盖领域、SQLite、迁移、真实临时目录仓储、Riverpod 控制器和 Widget；系统相册、权限、强停重启、真实大图和大字号留作用户手动设备验收。
