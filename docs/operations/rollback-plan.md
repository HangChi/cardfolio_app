# 回滚计划

## 1. 原则

移动端二进制无法保证即时撤回，且旧版本可能无法理解新 schema。因此“回滚”优先意味着暂停发布、关闭高风险远端能力、发布向前修复，并保护用户数据。

## 2. 触发条件

- 数据丢失、错误永久删除或大规模图片不可读；
- 数据库迁移失败率超过发布基线；
- 启动或保存失败显著上升；
- 安全或隐私泄露；
- Feature 010 出现不可控同步覆盖。

## 3. 操作

1. 暂停分阶段发布并保留证据。
2. 指定事件负责人和数据负责人。
3. 禁用可远端控制的高风险能力；本地核心浏览保持可用。
4. 判断是否可通过配置缓解或必须发布修复版本。
5. 不让用户安装会对新 schema 执行不安全降级的旧版本。
6. 使用备份/恢复或修复迁移恢复数据，并验证校验和与记录关系。
7. 对用户发布事实、影响、缓解和后续说明。

Feature 010 优先通过服务端开关停止新 push，保留 pull/数据下载与本地核心能力；不得
删除客户端 outbox 或把冲突策略降级为 last-write-wins。协议回滚只发布向前兼容网关，
旧客户端游标和操作 ID 必须继续可重放。账号删除通道不随普通同步开关关闭。

## 4. 数据库策略

迁移前创建恢复点或确保导出路径可用。迁移只向前，失败保留原文件并阻断启动；禁止自动删库。若必须恢复旧逻辑，发布能够读取当前 schema 的兼容修复版本。

## 5. 演练与复盘

Feature 008 和 Feature 010 上线前分别演练本地恢复与同步事故。每次真实事件记录时间线、根因、影响、恢复证据和防复发任务。
