## 1 产品概述

### 1.1 背景与机会

交通卡收藏者通常通过相册、电子表格、社交平台帖子或纸质卡册管理藏品。随着收藏数量增加，用户面临照片风格不统一、套卡完成度难追踪、购买成本分散、搜索效率低以及换机丢失资料等问题。

本产品以“拍照建档”为入口，以“长期整理和统计”为核心价值，首期聚焦交通卡，底层领域模型预留扩展至纪念卡、电话卡、票证等其他卡片类型的能力。

### 1.2 产品定位

> **一句话定位**
>
> 一款本地优先、可选云同步的交通卡收藏管理 App，让用户用统一、精美的图片保存藏品，并专业管理单卡、套卡、标签与收藏成本。

### 1.3 核心价值主张

| **价值** | **用户问题**                                       | **产品解法**                                                                   |
|----------|----------------------------------------------------|--------------------------------------------------------------------------------|
| 高效录入 | 拍照后需要手动裁图、调色、命名，录入耗时。         | 自动识别边缘、透视校正、基础增强、固定模板保存；支持连续和批量录入。           |
| 专业管理 | 同一套卡、多张重复卡、跨城市主题难以统一整理。     | 分离卡片款式、实体藏品、套卡、系列和标签；支持自定义字段、筛选与排序。         |
| 准确统计 | 不知道实际拥有多少张、累计花费多少、套卡还缺什么。 | 基于实体数量和购买记录统计总量、成本、进度与分布，避免套卡与单卡价格重复计算。 |
| 长期安全 | 换机或误删可能导致多年收藏资料丢失。               | 本地优先、回收站、导入导出、可选账号云同步与冲突副本。                         |

### 1.4 产品原则

- 不登录也能使用核心收藏管理功能。
- 默认私密；任何收藏内容不得未经用户明确操作公开。
- 保存先落本地，网络状态不能阻塞核心操作。
- 图片和结构化数据均应可导出、可迁移、可恢复。
- 首版优先保证录入稳定和管理准确，不以 OCR、社交或交易扩大范围。
- 统计必须可解释，任何金额汇总均可追溯到购买记录。

## 2 目标用户与核心场景

### 2.1 目标用户

| **用户类型** | **特征**                                             | **核心诉求**                                       |
|--------------|------------------------------------------------------|----------------------------------------------------|
| 核心收藏者   | 拥有数百至数千张交通卡，收藏时间长，重视资料完整性。 | 快速批量建档、套卡进度、精确查找、成本和数据安全。 |
| 轻量收藏者   | 收藏数量较少，以旅行纪念、城市主题为主。             | 简单好用、图片好看、能够按城市和主题浏览。         |
| 整理迁移者   | 已有相册或表格记录，希望转移到专业工具。             | 批量导入、字段映射、去重、数据导出。               |

### 2.2 典型用户画像

> **Persona A · 资深收藏者**
>
> 收藏 1,200 张交通卡，跨多个国家和城市；会整套购买，也会逐张补齐；最在意套卡完成度、重复卡数量、历史入手成本和数据备份。

> **Persona B · 旅行纪念收藏者**
>
> 每次旅行会保留地铁票、一日票或纪念储值卡；希望照片统一、按城市浏览、快速记录日期和地点，不愿在首次使用时注册账号。

### 2.3 核心任务（Jobs to Be Done）

1.  当我拿到一张或一套新卡时，我希望快速拍照并保存统一效果，以便未来准确识别和欣赏。
2.  当我的收藏越来越多时，我希望通过套卡、系列、标签和字段整理，以便快速找到任意一张卡。
3.  当我逐张补齐一套卡时，我希望知道已拥有、重复和缺失的成员，以便决定下一步收集目标。
4.  当我回顾收藏投入时，我希望看到累计花费并追溯每次购买，以便避免重复计算和失真。
5.  当我换手机、误删或暂时没有网络时，我希望收藏资料仍然安全可用。

### 2.4 非目标用户与非核心场景

- 以短期买卖、行情投机为主要目的的交易用户。
- 需要公开社交、粉丝运营或内容社区的创作者。
- 需要专业资产估值、保险估价或鉴定证书的机构。

## 3 产品目标与成功指标

### 3.1 产品目标

| **编号** | **目标**                     | **说明**                                                            |
|----------|------------------------------|---------------------------------------------------------------------|
| G-001    | 完成可靠的本地收藏闭环       | 用户可从图片导入/拍摄开始，完成建档、浏览、编辑、删除和恢复。       |
| G-002    | 将单张录入成本降到可持续水平 | 在不使用 OCR 的前提下，通过图片自动处理、默认值和批量复用减少步骤。 |
| G-003    | 建立可扩展的专业收藏模型     | 明确区分卡片款式、实体藏品、套卡、系列、图片和购买记录。            |
| G-004    | 提供可信的数量和花费统计     | 统计结果与业务规则一致，支持追溯和数据导出。                        |
| G-005    | 保障长期数据可迁移和可恢复   | 支持回收站、备份、导出；V1.0 提供可选云同步。                       |

### 3.2 关键成功指标

| **指标**            | **MVP 目标** | **V1.0 目标** | **口径**                                        |
|---------------------|--------------|---------------|-------------------------------------------------|
| 首次建档完成率      | ≥ 70%        | ≥ 80%         | 进入新建流程后成功保存至少一张卡的用户比例。    |
| 单卡建档中位时长    | ≤ 90 秒      | ≤ 60 秒       | 从选择/拍摄图片到保存成功；不含用户长时间停留。 |
| 7 日留存            | 观察基线     | ≥ 25%         | 首次保存卡片后的第 7 日仍打开 App。             |
| 核心操作崩溃率      | \< 0.5%      | \< 0.2%       | 拍摄、保存、导入导出、列表加载等核心路径。      |
| 导出-导入数据一致率 | 100%         | 100%          | 卡片、套卡、标签、购买记录和图片关联数量一致。  |
| 同步成功率          | 不适用       | ≥ 99%         | 排除用户取消和网络长期不可用。                  |

### 3.3 护栏指标

- 图片增强不得以明显降低可读性、改变卡面信息或裁掉关键内容为代价。
- 统计金额不得因套卡总价和单卡分摊价同时存在而重复累计。
- 云同步不得静默覆盖本地较新修改或删除用户未同步的数据。
- 新功能不得显著增加首次使用注册阻力。

## 5 领域模型与术语

### 5.1 核心对象结构

> **推荐结构**
>
> 收藏库 → 系列（可选）→ 套卡（可选）→ 卡片款式 → 藏品实例 → 图片。购买记录独立存在，并通过购买项目关联卡片或套卡。

### 5.2 术语定义

| **术语**                    | **定义**                                               | **示例**                                                     |
|-----------------------------|--------------------------------------------------------|--------------------------------------------------------------|
| 卡片款式（Card Definition） | 相同发行信息和卡面设计的一种卡；用于描述“这是什么卡”。 | 东京 Metro 2025 樱花纪念卡 01 浅草线。                       |
| 藏品实例（Card Item）       | 用户实际持有的实体卡；可记录数量、品相、入手信息等。   | 同款卡持有 3 张，可用一个实例 quantity=3，或按不同品相拆分。 |
| 图片（Card Image）          | 与藏品相关的正面、背面、包装、编号或细节照片。         | 正面 1 张、背面 1 张、包装 2 张。                            |
| 套卡（Card Set）            | 具有明确或预期成员数量、可计算完成度的一组卡。         | 全套 8 张，当前拥有 6 个不同成员。                           |
| 系列（Series）              | 用于宽泛归类的集合，不一定存在固定总数或完成度。       | 东京、世博会、生肖、东京 Metro。                             |
| 标签（Tag）                 | 用户自定义的轻量分类，可跨对象复用。                   | 单程票、一日票、储值票、城市、限定。                         |
| 购买记录（Purchase）        | 一次实际付款行为，是累计花费的事实来源。               | 2026-05-20 购买整套，支付 ¥450。                             |
| 购买项目（Purchase Item）   | 购买记录内关联的卡片、套卡或费用分摊。                 | 整套购买关联 8 个成员，但总花费只计一次。                    |

### 5.3 关系约束摘要

- 一张卡片款式可有多个藏品实例；一个藏品实例至少关联一个卡片款式。
- 一个藏品实例可拥有多张图片，图片需声明用途类型。
- 一个卡片款式最多归属于一个正式套卡，但可以加入多个系列。
- 套卡成员以“不同款式”计算完成度，重复实体不重复增加进度。
- 购买记录可同时包含多个卡片或一个整套；金额统计以购买记录为准。

## 7 核心用户流程

### 7.1 单卡快速建档

> **主流程**
>
> 首页/收藏 → 拍摄或相册导入 → 直接进入资料页 → 按需裁剪、旋转与调整 → 填写基本信息 → 添加标签 → 关联套卡/系列 → 记录购买（可跳过）→ 保存 → 卡片详情。

| **步骤** | **用户操作**       | **系统行为**                   | **异常/备选**                      |
|----------|--------------------|--------------------------------|------------------------------------|
| 1        | 选择拍摄或相册图片 | 申请权限并载入图片。           | 权限拒绝时说明用途并提供设置入口。 |
| 2        | 按需编辑图片       | 使用平台相册式裁剪、旋转和缩放。 | 取消或不可用时保留原图。          |
| 3        | 选择增强/模板      | 实时生成预览；默认保留原图。   | 处理失败时允许使用原图继续。       |
| 4        | 填写资料           | 提供最近值、默认值和可选字段。 | 必填缺失时定位到具体字段。         |
| 5        | 保存               | 事务性保存记录和受管理图片。   | 失败时保留草稿且不产生半条数据。   |

### 7.2 套卡连续录入

> **主流程**
>
> 创建/选择套卡 → 设置预计成员数（可未知）→ 逐张拍摄或批量导入 → 批量应用城市、机构、发行年份、购买记录 → 为各成员补充编号和名称 → 保存 → 套卡详情显示已拥有/缺失/重复。

### 7.3 整套购买与逐张补齐

- 整套购买：创建一条购买记录，记录总金额和包含的成员；统计只累计该购买记录总额。
- 逐张补齐：每次新增单卡购买记录；套卡完成度按不同成员更新，花费在购买记录层累计。
- 若用户同时填写套卡总价和单卡分摊价，单卡分摊只用于分析展示，不重复计入累计花费。

### 7.4 删除与恢复

> **流程**
>
> 卡片详情/批量操作 → 删除确认 → 移入回收站 → 从所有默认列表和统计中排除 → 用户在回收站恢复或永久删除。

### 7.5 云同步（V1.0）

> **本地优先数据流**
>
> 用户操作 → 立即写入本地数据库 → 记录待同步变更 → 网络可用时上传 → 服务端返回版本 → 更新本地同步状态。发生不可自动合并的冲突时，保留冲突副本，不静默覆盖。

## 10 数据模型概要

### 10.1 核心实体

| **实体**                    | **职责**                    | **关键字段（概要）**                                                                              |
|-----------------------------|-----------------------------|---------------------------------------------------------------------------------------------------|
| CardDefinition              | 描述一种卡片款式。          | id, name, type, city, issuer, issuedAt, issueQuantity, issuePrice, code, notes, setId, timestamps |

| CardSetMember               | 定义套卡成员和顺序。        | id, setId, definitionId, memberNo, required, sortOrder                                            |
| Series                      | 宽泛分类。                  | id, name, description, coverImageId                                                               |
| Tag / CardTag               | 用户标签及多对多关联。      | tagId, name, normalizedName, objectId                                                             |
| Purchase                    | 一次支付事实。              | id, purchasedAt, amount, currency, shipping, fees, channel, seller, notes                         |
| PurchaseItem                | 购买与卡片/套卡关联及分摊。 | id, purchaseId, targetType, targetId, allocatedAmount                                             |
| CustomFieldDefinition/Value | 用户定义字段及值。          | id, name, type, scope, value                                                                      |
| SyncRecord                  | 本地待同步队列与版本。      | id, entityType, entityId, operation, version, status, retryCount                                  |

### 10.2 通用字段与不变量

- 所有核心实体使用本地可生成的 UUID，避免离线创建依赖服务端。
- 所有可同步实体包含 createdAt、updatedAt、version；可删除实体包含 deletedAt。
- 数据库迁移必须版本化并具备自动化迁移测试。
- 结构化记录和图片文件保存需具备一致性补偿机制，防止孤儿文件或半条数据。
- 导出格式包含 schemaVersion，导入器必须明确支持的版本范围。

### 10.3 字段字典（卡片款式）

| **字段**      | **类型**         | **必填** | **规则**                                               |

| type          | Enum/String      | 否       | 交通卡首期预置：单程票、一日票、储值票、纪念卡、其他。 |

| issuer        | String/Reference | 否       | 发行机构或运营商。                                     |
| issuedAt      | Partial Date     | 否       | 支持只记录年份或年月。                                 |
| issueQuantity | Integer          | 否       | 大于 0；未知时为空。                                   |
| issuePrice    | Money            | 否       | 包含金额与币种，不计入用户花费。                       |
| code          | String           | 否       | 卡片编号、套卡成员编号或收藏编号。                     |
| notes         | Text             | 否       | 自由备注。                                             |

| NFR-A11Y-002 | 支持系统字体缩放；核心操作在较大字号下不得被裁切或不可点击。 |

### 11.4 兼容性与可维护性

| **需求 ID**  | **要求**                                                                     |
|--------------|------------------------------------------------------------------------------|
| NFR-PLAT-001 | 采用跨平台客户端，同一业务规则在 iOS 与 Android 行为一致。                   |
| NFR-ARCH-001 | 业务层不得直接依赖 UI、具体数据库或云服务实现。                              |
| NFR-TEST-001 | 所有业务规则、错误分支、数据迁移和核心用户路径必须具备自动化测试。           |
| NFR-OBS-001  | 正式发布前接入崩溃监控、错误日志和关键性能指标，且不上传卡面原图或敏感备注。 |

## 12 权限、隐私与数据安全

### 12.1 权限策略

| **权限**  | **申请时机**               | **用途说明**                                       | **拒绝后的降级**           |
|-----------|----------------------------|----------------------------------------------------|----------------------------|
| 相机      | 用户点击拍摄时             | 拍摄卡片照片。                                     | 仍可从相册导入或手动建档。 |
| 照片/媒体 | 用户点击导入或保存到相册时 | 读取用户选择的图片；可采用系统选择器减少广泛权限。 | 允许只使用相机或无图建档。 |
| 网络      | 启用登录、同步或更新资料时 | 云备份、同步和可选服务。                           | 核心收藏功能保持可用。     |

### 12.2 隐私要求

- 收藏、价格、卖家和备注默认仅用户本人可见。
- 不将卡片原图用于模型训练、广告或公共资料库，除非用户另行明确授权。
- 云端访问控制以用户为边界，图片对象不可通过可猜测公开 URL 访问。
- 支持数据导出、账户注销和云端数据删除。
- 错误日志不得包含完整卡面图片、自由备注、卖家联系方式或认证凭证。

### 12.3 安全要求

| **需求 ID** | **要求**                                                           |
|-------------|--------------------------------------------------------------------|
| SEC-001     | 认证令牌存储于平台安全存储，不写入普通偏好或日志。                 |
| SEC-002     | 云端传输使用 TLS；图片存储使用私有对象权限和短期授权访问。         |
| SEC-003     | 导出文件可能包含敏感信息，导出前展示内容说明；后续可增加加密备份。 |
| SEC-004     | 永久删除操作具有二次确认并清理结构化记录、缩略图、派生图和原图。   |

## 15 SDD + TDD 交付方式

### 15.1 规格分层

| **层级** | **文档**                                             | **用途**                                      |
|----------|------------------------------------------------------|-----------------------------------------------|
| 项目级   | PRD、领域词汇、业务规则、架构原则、非功能需求        | 定义长期边界和跨功能规则。                    |
| 功能级   | spec.md、acceptance.md、contracts.md、test-matrix.md | 定义单个可交付功能的行为与验收。              |
| 实施级   | plan.md、tasks.md                                    | 锁定文件结构、接口、任务依赖和逐步 TDD 操作。 |
| 代码级   | 测试、生产代码、迁移、变更日志                       | 以失败测试驱动最小实现并保持可追溯。          |

### 15.2 每个功能切片的必需工件

- 目标、用户价值、范围内和范围外。
- 正常、边界、失败、取消和恢复场景。
- Given / When / Then 验收标准。
- 输入、输出、错误、幂等性和事务边界契约。
- 规格到测试层级的追踪矩阵。
- 含精确文件路径、测试命令和小步提交的实施计划。

### 15.3 TDD 执行规则

> **Red → Green → Refactor**
>
> 每次从一条验收行为开始：先写最小失败测试并确认正确失败；再写使其通过的最少生产代码；运行目标测试和完整测试集；仅在全绿后重构并提交。

- 没有观察到正确失败的测试，不写对应生产代码。
- 一个测试聚焦一个可观察行为，避免测试私有方法和实现细节。
- 业务规则优先使用真实领域对象；仅在外部边界使用 Fake/Mock。
- 所有线上缺陷先添加可复现的失败回归测试。
- Spike 验证代码可例外，但不得直接进入生产路径；结论需要写入 ADR。

### 15.4 推荐的首个垂直切片

> **Feature 001 · 本地创建卡片闭环**
>
> 从相册选择一张图片 → 输入名称与基本资料 → 事务性保存 → 收藏列表显示 → 打开详情 → 应用重启后数据仍存在。此切片暂不包含相机、自动裁切、套卡、标签、购买、云同步。

### 15.5 功能进入开发的 Definition of Ready

| **检查项** | **要求**                                         |
|------------|--------------------------------------------------|
| 目标与范围 | 目标、用户价值、范围内、范围外明确，无关键 TBD。 |
| 术语与规则 | 使用领域词汇；相关 BR 和 NFR 已引用。            |
| 验收       | 正常、边界和失败场景可自动测试，每条有稳定 ID。  |

### 16.2 关键风险与缓解措施

| **风险**                           | **影响**                         | **缓解措施**                                                       |
|------------------------------------|----------------------------------|--------------------------------------------------------------------|
| 反光、透明或异形卡导致自动裁切失败 | 录入体验不稳定，是产品核心风险。 | 先做独立 Spike；提供手动四角、跳过增强和保留原图；建立真实样本集。 |
| 图片存储快速膨胀                   | 占用设备和云端空间，影响成本。   | 原图/派生图分层；缩略图；空间统计；可选择仅本地原图或删除原图。    |
| 卡片款式与实体模型过于复杂         | 用户理解成本高，UI 录入繁琐。    | 界面默认使用“卡片”，仅在重复/品相场景暴露实体高级选项。            |
| 成本统计口径争议                   | 用户不信任统计结果。             | 购买记录为唯一事实来源；口径说明和下钻；按币种分组。               |
| 本地优先同步冲突复杂               | 可能造成数据丢失或重复。         | 同步作为独立里程碑；幂等操作；版本号；冲突副本；大量自动化测试。   |
| 范围不断扩大                       | 延期并削弱核心体验。             | 坚持 P0/P1/P2；新增需求必须先更新 Spec、优先级和替代项。           |

### 16.3 已确认的产品决策

| **决策**   | **结论**                                             |
|------------|------------------------------------------------------|
| 品类范围   | 首版聚焦交通卡，数据结构支持未来扩展到其他卡片。     |
| 体验优先级 | 高效录入 + 专业管理优先，兼顾精美展示。              |
| 客户端     | iOS + Android 跨平台开发。                           |
| 数据策略   | 本地优先，不登录也可用；登录后可选云同步。           |
| 图片结构   | 单个藏品支持多图；多张卡通过套卡/系列组织。          |
| 价格结构   | 同时支持整套总价和单卡价格/分摊，统计避免重复计算。  |
| 智能识别   | OCR 与资料库只提供候选，用户逐项确认后才写入资料。   |

### 16.4 待后续 Spec 决定的事项

- 主币种换算的汇率来源、历史汇率口径和离线策略。
- 云同步服务端选型、存储配额、冲突自动合并粒度。

- 原图默认保留策略与免费/付费云空间模型。
